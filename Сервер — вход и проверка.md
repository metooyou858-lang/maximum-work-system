## Коротко для владельца

Для обычной работы достаточно написать Codex: «Проверь сервер по инструкции “Сервер — вход и проверка.md”». Повторно отправлять пароль не нужно. Проверка не перезагружает сервер и не исправляет настройки автоматически.

С этого компьютера, в PowerShell из папки проекта:

```powershell

.\ops\connect-test-vps.ps1

# Или выполнить проверку и завершить соединение
.\ops\check-test-vps.ps1
```

## Процедура для Codex

1. Прочитать эту инструкцию и `AGENTS.md`. Проверить наличие ключа и DPAPI-файла, не выводить их содержимое.
2. До запуска SSH расшифровать парольную фразу внутри `functions.exec`: вызвать `tools.exec_command` с PowerShell-командой ниже, сохранить `result.output.trim()` в закрытую переменную/`store`. Сам `result` и фразу не передавать в `text`, commentary или финальный ответ. Проверить `exit_code`.

   ```powershell
   $taskSecure = Get-Content -LiteralPath "$env:USERPROFILE\.ssh\maximum_vps.passphrase.dpapi" | ConvertTo-SecureString
   [System.Net.NetworkCredential]::new('', $taskSecure).Password
   ```

   Эта команда предназначена только для захвата результата в память оркестратора. Не запускать её отдельным вызовом, печатающим результат в чат/терминал. Не включать транскрипцию PowerShell или отладочную печать секретов.

3. Запустить `ops/check-test-vps.ps1` либо `ops/connect-test-vps.ps1` через `tools.exec_command` с `tty: true`. В текущей песочнице SSH заблокирован заглушкой; использовать штатный `sandbox_permissions: require_escalated` с описанием конкретной операции, а не обход через другой ssh.exe.
4. Дождаться именно `Enter passphrase for key ...maximum_vps`. Через `tools.write_stdin` передать сохранённую фразу + `\r`. Не вставлять секрет в строку shell-команды. На ввод отведено около 30 секунд, поэтому фразу загружать заранее.
5. Дочитать результат до завершения. Для диагностики сохранить только очищенный вывод проверок и код завершения; для интерактивного входа выполнять необходимые команды, затем `exit`.
6. Удалить фразу из временного `store`/переменной. Не снимать шифрование ключа, не менять секреты при обычной проверке.

Если автоматическая проверка отклоняет действие, не обходить её. Сообщить конкретную причину и продолжать только разрешённые операции.

Прямая команда подключения, эквивалентная сценарию:

```powershell
ssh -i "$env:USERPROFILE\.ssh\maximum_vps" -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=15 -p 22 maximum-admin@89.125.214.188
```

Не удалять `known_hosts` и не применять `StrictHostKeyChecking=no` при предупреждении о смене ключа. Сначала выяснить, переустанавливался ли VPS, и сверить новый отпечаток через доверенную консоль провайдера.

## Статус диагностического сценария

`ops/check-test-vps.ps1` передаёт текущий `ops/check-test-vps.sh` в SSH-сеанс и выполняет его через sudo. Файл на сервере не устанавливается. Однако скрипт написан для прежнего контура с PostgreSQL и резервными копиями. На 30.09.2026 он **не является** диагностикой текущего VPS и не подтверждает готовность приложения, карты или HTTPS.

До развёртывания приложения безопасная базовая диагностика включает: вход по ключу, `sudo -n`, состояние SSH/UFW/Fail2ban, фактические правила UFW, версии Node.js и Caddy, свободные диск и память. После развёртывания скрипт нужно заменить проверкой службы приложения, Caddy/сертификата, SQLite-копии и отсутствия секретов в выводе. До этого старые пункты ниже оставлены только как архив прежнего контура.

- UFW действительно активен и запрещает входящие по умолчанию; вывод правил позволяет проверить исключения.

- Последняя локальная копия не старше 26 часов, её каталог читается `pg_restore --list`, последнее задание завершилось успешно.
- Проверяются диск, доступная память, swap, необходимость перезагрузки и состояние пакетов.
- Выводятся слушающие TCP-порты: в текущей конфигурации ожидается публичный SSH на 22 и локальный DNS. Новые публичные порты требуют объяснения.

Код завершения: `0` — проверки пройдены; `1` — предупреждения; `2` — обнаружены неисправности. Ошибка соединения SSH обычно даёт `255`; ошибка запуска PowerShell может дать другой код. Надпись `RESULT` должна присутствовать, иначе нельзя считать диагностику завершённой.

Пороги: диск от 80% — предупреждение, от 90% — ошибка; доступная RAM ниже 200 MiB — предупреждение. Это рабочие пороги тестовой среды, а не измерение производительности будущего приложения.

## Если обнаружена проблема

| Симптом | Действия |
|---|---|
| Timeout / refused | Проверить оплату и состояние VPS в панели, внешний порт 22 и доступность сети. После перезагрузки дать системе 30–60 секунд. Не менять SSH-порт наугад |
| Permission denied | Проверить пользователя maximum-admin, путь ключа и ввод его фразы; root и пароль заведомо не подходят. Не повторять ошибочный вход сериями: работает Fail2ban |
| DPAPI не расшифровывается | Проверить, что используется исходная учётная запись Windows. Не удалять ключи и не создавать замену поверх старого файла |
| Host key changed | Остановить вход и проверить причину через панель/консоль провайдера |
| UFW inactive | Через доступный SSH/консоль проверить `systemctl is-enabled ufw`, `ufw show added`. В образе провайдера служба была masked; восстановление описано ниже |
| Архивная база недоступна | Относится к прежнему PostgreSQL-контуру, не применять к текущему VPS |
| Архивная копия устарела | Относится к прежнему заданию PostgreSQL-копирования, не применять к текущему VPS |

Восстановление UFW при подтверждённой неисправности (из рабочей административной сессии/консоли):

```bash
sudo -n bash -c 'ufw allow 22/tcp && systemctl unmask ufw && systemctl enable --now ufw && ufw --force enable && ufw status verbose'
```

После любых изменений SSH/UFW сохранить текущую сессию и проверить вход второй сессией. При изменении SSH использовать отложенный откат по образцу `ops/harden-ssh.sh`; не перезапускать этот первоначальный сценарий вслепую. После плановой перезагрузки обязательно повторить полную диагностику.

Если SSH полностью недоступен, нужна аварийная консоль провайдера. Войти как root с новым аварийным паролем из DPAPI-хранилища; проверить службы SSH/UFW, NAT и блокировки Fail2ban. Не отключать всю защиту ради проверки. Доступность консоли пока не подтверждена.

При утрате компьютера могут быть одновременно утрачены и ключ, и возможность расшифровать DPAPI. Тогда восстановление выполняется через аккаунт хостинга/поддержку и новый публичный ключ. Независимое защищённое хранение аварийных реквизитов и проверка консоли остаются открытыми задачами — эта инструкция не заменяет резерв доступа.
