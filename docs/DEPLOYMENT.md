# Обязательный регламент публикации на тестовый VPS

Этот порядок применяется при каждой публикации файлов в рабочий контур. Нельзя пропускать пункты, заменять их предположением или сообщать о готовности до пункта 9.

1. Прочитать `AGENTS.md`, `docs/OPERATIONS.md` и «Сервер — вход и проверка.md». Проверить список публикуемых файлов и не включать чужие незавершённые изменения.
2. До SSH расшифровать парольную фразу только в закрытой памяти оркестратора. Проверить, что полученная строка не пуста. Не ограничивать вывод команды расшифровки так, чтобы значение могло быть потеряно; не печатать фразу ни в терминал, ни в сообщения.
3. Подключаться только штатным `ops/connect-test-vps.ps1` либо `ops/check-test-vps.ps1`. Для SCP использовать те же параметры идентификации сервера: `IdentitiesOnly=yes`, `HostKeyAlias=maximum-vps-371333-current`, `StrictHostKeyChecking=yes`. Не отключать проверку ключа и не менять `known_hosts` при предупреждении.
4. Перед изменением схемы БД или серверного кода проверить `maximum-work.service` и создать свежую резервную копию через `maximum-backup.service`. Убедиться, что новый файл дампа появился в `/var/lib/maximum/backups`.
5. До замены рабочих файлов проверить синтаксис передаваемых файлов локально и на VPS в `/tmp`. Сначала передавать файлы только во временный каталог `/tmp`.
6. Устанавливать проверенные файлы из `/tmp` в `/srv/maximum` через `sudo -n install` с владельцем `maximum`. Секреты и файлы окружения не передавать в репозиторий или `/tmp`.
7. Если менялись серверный код, окружение или схема — выполнить `systemctl daemon-reload` при необходимости и перезапустить только `maximum-work.service`. Убедиться, что служба имеет состояние `active`.
8. Проверить публичный HTTPS-адрес `/manager/` и отсутствие ошибок службы. Проверки БД, API и `active` не являются финальной приёмкой.
9. Войти через опубликованную форму и пройти весь затронутый путь в браузере на VPS: действие пользователя, сохранение, повторное открытие и проверка результата. Использовать только синтетические данные. При ошибке исправлять и повторять с пункта 5.
10. Очистить парольную фразу, SSH/SCP-сеансы и временные значения из закрытого хранилища оркестратора. В финальном сообщении назвать только фактически пройденные проверки и оставшиеся внешние блокеры.

Если парольная фраза не принята, сначала проверить, что она была корректно получена из DPAPI и передана в активный запрос SSH. Не выдавать это за отказ сервера, пока не получено фактическое сообщение SSH об отказе аутентификации.
